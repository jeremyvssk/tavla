# Database Migrations

Flyway owns the schema. Migrations live in `backend/src/main/resources/db/migration/` and run
automatically at application startup. JPA is `ddl-auto: validate` — Hibernate never creates or
alters anything, it only checks the entities match what Flyway built. A mismatch fails the app at
boot, which is the point.

## The one unbreakable rule

**Migrations are append-only.** Never edit a `V*.sql` that has been committed or applied anywhere.
Flyway stores a checksum in `flyway_schema_history`; changing the file makes every existing
database refuse to start. Fix a mistake with a *new* migration.

The only time editing is legitimate: the migration exists solely in your working tree, has never
been committed, and you have wiped the volume since. If in doubt, add a new file.

## Naming

`V<n>__<snake_case_description>.sql` — two underscores. Numbers are sequential with no gaps.
Existing history:

```
V1__initial_schema.sql
V2__oauth_nullable_password.sql
V3__widen_two_factor_backup_codes.sql
```

Descriptions say what changed, not what it is for: `V4__catalog_search_indexes.sql`, not
`V4__make_search_fast.sql`.

## What belongs in the schema

Constraints are facts; application-level checks are hopes. Mirror every DTO rule down into SQL:

| DTO annotation | Schema |
|---|---|
| `@NotBlank` / `@NotNull` | `NOT NULL` |
| `@Size(max = N)` | `VARCHAR(N)` |
| `@Min` / `@Max` / `@DecimalMin` | `CHECK` |
| uniqueness | `UNIQUE` constraint or unique index |

Foreign keys need a deliberate `ON DELETE` rule — this schema uses all three, on purpose:
`RESTRICT` when the parent must not disappear out from under children (`products.category_id`),
`SET NULL` when the child outlives the parent (`products.brand_id`), `CASCADE` when the child is
meaningless alone (`product_images`, `product_reviews`). Pick one consciously and be able to
defend it.

## Postgres features this schema depends on

Do not write these in a way H2 or MySQL would accept — portability is not a goal here, and the
tests run on real Postgres precisely because of this list.

- `JSONB` for `products.attributes`, so new product types need no migration
- `TSVECTOR GENERATED ALWAYS AS (...) STORED` for `products.search_vector` — maintained on write
- **Partial indexes**, e.g. `uq_categories_root_name ... WHERE parent_id IS NULL`
- **GIN** indexes for full-text search over `tsvector`, and `pg_trgm` for autocomplete —
  `CREATE EXTENSION IF NOT EXISTS pg_trgm;` belongs in the migration that first needs it
- `UUID` primary keys on `users`, `products`, `product_reviews`; `INTEGER GENERATED BY DEFAULT AS
  IDENTITY` on the lookup tables

A generated column cannot reference another generated column, and its expression must be
`IMMUTABLE` — that is why `search_vector` pins `to_tsvector('english', ...)` with an explicit
config rather than relying on the session default.

## Verifying it applied

```sh
docker compose up -d --build backend
docker compose logs backend | grep -i flyway

docker compose exec postgres psql -U app -d iloveshopping -c '\dt'
docker compose exec postgres psql -U app -d iloveshopping -c '\d products'
docker compose exec postgres psql -U app -d iloveshopping -c 'SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;'
```

Every row in `flyway_schema_history` must show `success = t`. To start from nothing:
`./start.sh reset` drops the volumes.

Confirm an index is actually *used*, not merely present — `EXPLAIN ANALYZE` the query it was added
for. An unused index is cost with no benefit, and it is the classic thing a green test suite will
never tell you about.
